### 3a. The `ai` peer dependency

Current: `ai` 7.0.126 is latest; we are on v4 (3 majors behind). `@ai-sdk/openai` latest 4.0.83 vs our exactly-0.0.42. `ollama-ai-provider` 1.2.0 is the v4-era community package; `ollama-ai-provider-v2` 4.0.1 exists. Anyone with a modern AI SDK app gets unresolvable peer conflicts.

**Does `defineTool`/`ToolDescriptor` still depend on the v4 `tool()` shape? Yes.**
- `ToolDescriptor.tool: AITool` (`src/types/tool.ts:1,37`) is the `ai` v4 `Tool` type.
- `defineTool()` builds `tool({ description, parameters: opts.input, execute })` (`src/tools/defineTool.ts:134-138`) and types `ctx` as `ai`'s `ToolExecutionOptions` (`:1,31`; also `src/execution/sandboxGuard.ts:21`).
- The loop reads `toolDesc.tool.parameters` to build tool definitions and to validate args (`src/execution/generateStep.ts:47`, `src/execution/toolArgsValidation.ts:92`).
- 54 `tool({ parameters: z... })` calls in built-ins (`github.ts` 28, `jira.ts` 20, `http/slack/email/currentDate/dayName` 1 each) plus `src/execution/DelegationTool.ts:8` and `src/tools/mcp/McpToolLoader.ts:10,118-123`.
- Provider adapter uses v4 names: `CoreMessage`, `ToolCallPart.args`, `ToolResultPart.result`, `maxTokens`, `maxSteps: 1`, `usage.promptTokens/completionTokens` (`src/providers/aiSdkProvider.ts:16-28,81-110,177-182,297-311`); `src/types/agent.ts:1` imports `CoreMessage`; `src/execution/errors.ts:6` imports `APICallError`, `LoadAPIKeyError`, `RetryError`.
- v6 names as used by open-harness: `inputSchema`, `ModelMessage`, `stopWhen: stepCountIs(n)`, `maxOutputTokens`, `inputTokens/outputTokens` ([agent.ts](https://github.com/MaxGfeller/open-harness/blob/main/packages/core/src/agent.ts), [create-bash-tool.ts](https://github.com/MaxGfeller/open-harness/blob/main/packages/core/src/tools/create-bash-tool.ts)); eve (v7) uses `ModelMessage`, `UserContent`, `jsonSchema` from `ai` (grep of `packages/eve/src`).

Good news: the executor, `mockModel`, `recordReplay`, sessions and stores speak our own `LLMProvider`/`Message` types (`src/providers/llm.ts`), so the upgrade is confined to ~20 files: `src/providers/aiSdkProvider.ts` + 4 provider files, `src/types/{tool,agent}.ts`, `src/tools/**`, `src/execution/{generateStep,toolArgsValidation,sandboxGuard,errors,DelegationTool}.ts`, 4 test files that import `ai`, the scaffold template and Forge's `package.json`.

## 7. Differentiators (where we can win outright)

1. **Host-agnostic durable sessions in one option.** eve's durability needs the Workflow SDK runtime (Nitro server, Node 24, local or Postgres world, [execution-model-and-durability.mdx](https://github.com/vercel/eve/blob/main/docs/concepts/execution-model-and-durability.mdx)); open-harness saves only at turn end. Design: `createAgent({ store })` where `store` implements one `AgentStore { sessions, checkpoints, approvals }` (already true of `SqliteStore`, `src/storage/sqlite/SqliteStore.ts`; add `FileStore`, `KVStore` for Workers/D1, `PostgresStore`). `agent.session(id)` checkpoints after every model turn and tool batch (U9), appends new input on resume (U8), and `session.resume()` continues a crashed turn in any process, including a Cloudflare Worker. Each checkpoint records an agent fingerprint (prompt + tool names + model) so a resumed run can refuse or warn on drift, the in-process analogue of eve finishing a session on the deployment it started on. Tickets: W9, D30, D43.
2. **Record/replay as the default test and eval substrate.** We already ship `mockModel` and `recordReplay` (`src/testing/`); eve has only `mockModel` ([evals/overview.mdx](https://github.com/vercel/eve/blob/main/docs/evals/overview.mdx)); open-harness has nothing. Design: `loushy eval --record` runs evals against real models once and writes cassettes next to each `*.eval.ts`; CI runs `--replay` (deterministic, free); `--drift` re-records and diffs trajectories (tool sequence, args, step count, cost) into the JUnit report so a model or prompt change shows up as a reviewable diff. Tickets: D46.
3. **Agent Forge time-travel.** Neither competitor has a visual debugger (eve has a TUI, [dev-tui.md](https://github.com/vercel/eve/blob/main/docs/guides/dev-tui.md)). Design: stores keep checkpoint history per session (D43); `AgentExecutor.fork({ sessionId, fromStep, patch: { prompt?, toolResult? } })` creates a new session from step N (D44); Forge shows the step list with cost/tokens per step and an "edit and replay from here" action, with the two trajectories side by side (D45). Combined with record/replay, a replay from step N can reuse cassette responses for the unchanged prefix.
4. **Be reachable from everything: MCP server + ACP + HTTP.** We already export an agent as an MCP server (`src/tools/mcp/server/serveMcp.ts`), which open-harness lacks. Add `loushy acp` (Z6) mapping ACP permission requests onto our approvals, and the D14 HTTP session API, so one agent definition serves Claude Code/Zed/editors, other agents and web UIs without a framework runtime. Tickets: Z6, D14, Y7.
5. **Both authoring modes, one runtime, hot reload for both.** eve is directory-first (programs talk to a server via `eve/client`); open-harness is code-only. `loadAgentDir()` already compiles a directory to `createAgent()` options (`src/agentDir/loadAgentDir.ts`). Design: `loushy dev <dir|file.ts|spec.yaml>` serves all three with hot reload (cache-busted dynamic import of tools), a stateful streaming chat with approval buttons, and the same events as production. Tickets: D31, D32, D33.
6. **OTel GenAI conventions plus cost, out of the box, on any backend.** We emit `gen_ai.*` spans (`src/execution/semconv.ts`, `genAiSpans.ts`) and per-step USD (`src/execution/runUsage.ts`); open-harness has no tracing; eve's best experience is Vercel-hosted. Design: add GenAI metrics (`gen_ai.client.token.usage`, `gen_ai.client.operation.duration`), a `loushy.cost_usd` attribute per span, sub-agent span linking (already inherited via LOU-Y1), and an `examples/` page per backend (Jaeger, Honeycomb, Langfuse). Ticket: D48.
7. **Trajectory evals that run anywhere and gate CI.** We have `t.calledTool`, `t.completed`, judges and `--junit` (`src/evals/trajectory.ts`, `src/cli/eval.ts`) running in-process under vitest, no server boot (eve's runner boots a server, [evals/overview.mdx](https://github.com/vercel/eve/blob/main/docs/evals/overview.mdx)). Add a remote target (`--url`, D47) and cassettes (D46) to cover both fast local CI and post-deploy smoke tests from one file.
8. **Edge-native agents.** eve requires Node 24 and a Nitro server; open-harness is Node-only (`NodeFsProvider`, `NodeShellProvider`). Our Worker target with KV checkpoints (`src/deploy/adapters/cloudflare.ts`) is unique; finishing D14 (sessions + SSE + auth) on the Worker target and adding schedules as Worker cron triggers (P9) makes "deploy a durable agent to the edge in one command" a claim neither competitor can make.
